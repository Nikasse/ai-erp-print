# AI Prompt Notes — Урок 10

Документація роботи над промптом для AI-аналізу транзакцій
(`app/prompts.py`, `app/api.py`, `POST /api/ai/analyze-transactions`).

## 1. Навіщо цей документ

Промпт — це частина backend-логіки продукту, а не текст "для краси".
Він так само визначає поведінку системи, як і код: неточне формулювання
може призвести до вигаданих цифр, відповіді не тією мовою чи
непридатного для парсингу формату. Тому рішення щодо промпту й
результати експериментів фіксуються тут так само, як фіксувались би
рішення щодо коду в PR-описі чи коментарях.

## 2. Слабкий vs сильний промпт

### SYSTEM_WEAK (не використовується в продакшені)

```
Ти фінансовий аналітик. Проаналізуй фінанси.
```

### SYSTEM_STRONG (робочий, використовується в `/api/ai/analyze-transactions`)

```
Ти досвідчений фінансовий аналітик, який готує короткий звіт для власника
особистого чи невеликого бізнес-бюджету.

Суворі правила:
- Спирайся ТІЛЬКИ на дані, передані нижче у зведенні. Не вигадуй суми,
категорії, дати чи операції, яких там немає.
- Якщо операцій замало для впевнених висновків (наприклад, дуже мало
операцій або короткий період) — прямо скажи про це у summary, а не
додумуй.
- Відповідай виключно українською мовою.
- Відповідь має бути строго валідним JSON без markdown-обгортки
(без ```), без жодного тексту до чи після JSON.

Формат JSON:
{"summary": string, "top_expense_categories": [string],
"risks": [string], "advice": [string]}
```

### Чого бракує SYSTEM_WEAK

| Що відсутнє | Наслідок без цього | Як вирішено в SYSTEM_STRONG |
|---|---|---|
| **Роль моделі** | "Фінансовий аналітик" — надто загальне формулювання, не задає ні аудиторію, ні мету звіту | Роль конкретизована: "готує короткий звіт для власника особистого чи невеликого бізнес-бюджету" |
| **Заборона вигадувати дані** | Модель може домислити суми, категорії чи операції, яких не було в наданих даних — особливо на малих вибірках | Явна вимога "Спирайся ТІЛЬКИ на дані... Не вигадуй суми, категорії, дати чи операції" |
| **Правило для випадку "даних мало"** | На 0–2 операціях модель за замовчуванням намагається видати впевнений аналіз, бо про інший варіант поведінки її не попередили | Окремий пункт: якщо операцій замало — сказати про це прямо в `summary`, а не додумувати |
| **Мова відповіді** | Мова відповіді не гарантована — залежно від мови вхідних даних модель може відповісти англійською | Явна вимога "Відповідай виключно українською мовою" |
| **Формат відповіді** | Без вимоги формату модель повертає вільний текст (можливо, з markdown-форматуванням), що неможливо надійно розпарсити на бекенді | Вимога строго валідного JSON без markdown-обгортки + точна схема полів (`summary`, `top_expense_categories`, `risks`, `advice`) |

## 3. Сирі операції vs backend-зведення

До рефакторингу промпт для моделі будувався з сирих рядків операцій
(`дата | тип | сума | категорія | опис` для кожної з до 100 операцій).
Після рефакторингу (`app/prompts.py`) той самий обсяг даних попередньо
згортається на бекенді через `build_summary()` (підсумки, суми по
категоріях, топ-5 витрат, період, кількість без категорії), і в модель
іде вже компактний текст із `build_prompt()` — без технічних id та
`created_at` кожної окремої операції.

Інструмент для заміру — `check_tokens.py` (корінь проєкту): бере
реальні операції з бази, будує обидва варіанти промпту (сирий і
зведення) з однаковим `SYSTEM_STRONG`, рахує `input_tokens` для
кожного через `client.messages.count_tokens()` і друкує таблицю з
різницею у відсотках.
