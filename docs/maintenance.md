# Підтримка production

Що робити після того, як проєкт уже задеплоєний: як перевіряти зміни перед
merge, де дивитись логи, і як діяти, коли production зламався.

Пов'язане: [deploy.md](deploy.md) — як влаштований деплой,
[domain.md](domain.md) — домен і DNS, [../AGENTS.md](../AGENTS.md) — межі й
контракти проєкту.

## 1. Навіщо AGENTS.md

[../AGENTS.md](../AGENTS.md) — контекст, який AI-асистент читає **перед**
зміною коду: межі, API-контракти, правила роботи з секретами.

AI бачить код, але не бачить домовленостей. З коду не видно, що:

- `app/render_app.py` — production entry point, а `app/api.py` — ні;
- `Dockerfile` збирає образ бота, а не сайту;
- шляхи `/api/*` не можна перейменовувати, бо на них зав'язана адмінка;
- AI-дія має пройти через `pending_actions` і підтвердження людиною, а не
  писатись у базу напряму.

Усе це — рішення, а не властивості коду. Без AGENTS.md кожна нова сесія
починається з нуля і повторює ті самі помилки: правку в `app/api.py`
замість `render_app.py`, «зручний» новий роут поверх наявного, секрет
у коді «на час тесту».

## 2. Як запустити preflight

```bash
python3 scripts/preflight.py
```

П'ять перевірок по порядку — [../scripts/preflight.py](../scripts/preflight.py):

| # | Перевірка | Що робить |
|---|---|---|
| 1 | Python compile | компілює всі `.py` у `app/` і `scripts/` |
| 2 | React build | `npm ci` + `npm run build` в `admin/` |
| 3 | Docker build | збирає образ з `Dockerfile.render` |
| 4 | Secret scan | шукає секрети у файлах під git |
| 5 | Config check | `.env` поза git, критичні файли на місці |

Скрипт зупиняється на **першій** помилці — далі не йде. У кінці друкує
`PREFLIGHT PASSED` (exit code 0) або `PREFLIGHT FAILED` (ненульовий exit
code), тому його можна ставити кроком у CI без обгорток.

```
[1/5] Python compile ... OK
[2/5] React build ... OK
[3/5] Docker build ... SKIPPED (docker daemon not running)
[4/5] Secret scan ... OK
[5/5] Config check ... OK
PREFLIGHT PASSED
```

**`SKIPPED` на Docker build — це не збій.** Дві причини: docker не
знайдено в PATH або демон не відповідає (Docker Desktop закритий). Preflight
у цьому разі проходить далі й може завершитись `PASSED` — образ усе одно
збереться в CI і на Render, тож перевірка не втрачається, а відкладається.
Усі інші чотири перевірки `SKIPPED` не мають: вони або `OK`, або `FAILED`.

Дрібниці, які корисно знати:
- прогін з docker-збіркою займає хвилини, не секунди;
- перевірка 2 створює `admin/node_modules` і `admin/dist` — обидва в
  `admin/.gitignore`, у git не потраплять;
- перевірка 4 друкує лише файл і номер рядка, ніколи саме значення;
- якщо знахідка хибна, у рядок додається `pragma: allowlist secret` — той
  самий маркер, що вже використовує `.secrets.baseline`.

## 3. Що перевіряє GitHub Actions

[../.github/workflows/preflight.yml](../.github/workflows/preflight.yml)
запускає **той самий** `scripts/preflight.py` — не окремий набір перевірок.
Workflow лише готує середовище і викликає скрипт. Якби перевірки
дублювались у yml, локальний і серверний набори з часом розійшлися б.

| | |
|---|---|
| Тригери | `pull_request` з target `main`, `push` у `main` |
| Runner | `ubuntu-latest` |
| Python | `3.12` — як у фінальній стадії `Dockerfile.render` |
| Node | `20` — як у build-стадії `Dockerfile.render` |
| Секрети | не передаються жодні |

Версії збігаються з `Dockerfile.render` навмисно: інакше CI перевіряв би не
те середовище, яке піде в production.

**Секретів у CI немає.** Preflight не звертається ні до Neon, ні до
Anthropic API — він компілює код, збирає фронтенд і образ, шукає секрети в
git-файлах. Ні `DATABASE_URL`, ні `ANTHROPIC_API_KEY`, ні `BOT_TOKEN` йому
не потрібні. Якщо колись перевірка почне вимагати секрет — це сигнал, що
вона вийшла за межі preflight.

**На runner'і docker є**, тому в CI крок Docker build реально виконується і
`SKIPPED` не буває — образ `Dockerfile.render` збирається на кожному PR.

**Гілка `main` захищена**: preflight — required check. Merge без зеленого
preflight заблокований, у `main` не потрапляє код, який не компілюється,
не збирається або містить секрет.

## 4. Як Render запускає deploy

Auto-deploy при push у `main`. Runtime — Docker, Dockerfile Path —
`./Dockerfile.render`. Деталі збірки: [deploy.md](deploy.md), розділи 2–3.

**CI і Render незалежні.** Actions перевіряє код, Render деплоїть — це два
різні сервіси, які нічого одне про одного не знають. Render **не чекає** на
зелений preflight: він реагує на сам push у `main` і почне збірку навіть
якщо Actions у цей момент падає.

Наслідок: те, що не пускає зламаний код у production, — це **захист гілки**
(розділ 3), а не Render. Push напряму в `main` в обхід PR = deploy без
жодної перевірки.

## 5. Де читати production logs

Render → сервіс → **Logs**. Live tail, оновлюється в реальному часі; там же
видно і build log, і рантайм-вивід uvicorn.

Free tier: **немає SSH і немає one-off jobs** — залізти в контейнер,
запустити скрипт чи подивитись файли неможливо. Діагностика тільки через
логи в панелі.

Дві речі, які збивають з пантелику при читанні логів (детально —
[deploy.md](deploy.md), розділ 6):

- `"HEAD / HTTP/1.1" 405 Method Not Allowed` — це **не** помилка, а
  HEAD-пінг Render у catch-all роут, зареєстрований на `GET`;
- `"LLM недоступний"` у відповіді API **не потрапляє** в логи з причиною —
  виклик обгорнутий у `except Exception` без логування. Обрізаний ключ,
  відсутній ключ і збій Anthropic виглядають однаково; перевіряти треба
  саму змінну в Environment.

## 6. Що входить у smoke test після deploy

Мінімальний прогін, який показує, що працює весь ланцюг:
домен → Render → FastAPI → Neon.

```bash
curl https://home-base.pp.ua/health
curl https://home-base.pp.ua/api/summary
curl https://home-base.pp.ua/api/transactions
```

| Перевірка | Очікувано |
|---|---|
| `/health` | `{"status":"ok","env":"production"}` |
| `/api/summary` | JSON з `total_income`, `total_expense`, `balance` |
| `/api/transactions` | JSON-масив операцій |
| Адмінка | `https://home-base.pp.ua` відкривається, показує картки й таблицю |
| Створення операції | форма зберігає операцію без помилки |
| Запис на місці | операція видна **і в списку адмінки, і в базі Neon** |

Останній пункт — суть smoke test. Адмінка може показати операцію з
локального стану, тому перевіряються обидва рівні: після перезавантаження
сторінки запис лишається в таблиці (значить прийшов з `/api/transactions`),
і він же видно в Neon → SQL Editor:

```sql
select id, amount, description, created_at
from transactions
order by created_at desc
limit 5;
```

Операції, створені через API, привʼязані не до Telegram-користувача, а до
спільного системного користувача `api` (`telegram_id = -1`) — так і має
бути, це не аномалія.

Перший запит після простою може йти 30–60 с: піднімається контейнер, потім
прокидається Neon. Це free tier, не поломка ([deploy.md](deploy.md),
розділ 8).

Перевіряти звичайним `GET`. `curl -I` шле `HEAD` і отримає `405 allow: GET`
— теж не помилка ([domain.md](domain.md), розділ 7).

## 7. Коли маленький fix, а коли rollback

| Ситуація | Дія |
|---|---|
| Причина зрозуміла, правка мала | fix |
| Production зламаний, причина неясна | rollback |

Порядок саме такий: **спершу стабілізувати production, потім шукати
причину.** Поки сайт лежить, дебаг у production — це дебаг на користувачах.
Відкат повертає робочий стан і дає час розібратися спокійно.

Не робити хаотичних правок наосліп. Кожен «а спробуємо ще так» — це новий
deploy, нові 2–5 хвилин збірки й ще одна змінна в рівнянні: після п'ятої
такої правки вже не зрозуміти, що саме зламало, а що полагодило.

## 8. Як виконати git revert

```bash
git revert <commit_hash>
```

Створює **новий** коміт, який скасовує зміни попереднього. Історія
зберігається, нічого не переписується — на відміну від `reset --hard`, який
затирає комміти і ламає історію в усіх, хто вже її забрав.

Далі — звичайний процес: гілка → PR → merge. `main` захищена (розділ 3),
тому revert теж проходить через PR і preflight. Це не бюрократія: відкат —
така сама зміна коду, і вона так само може не збиратися.

Якщо відкочується merge-коміт (а історія проєкту складається саме з
merge-комітів PR-ів), потрібен номер сторони:

```bash
git revert -m 1 <merge_commit_hash>
```

`-m 1` означає «лишити стан гілки, в яку зливали» — тобто скасувати те, що
принесла злита гілка.

## 9. Як повернути попередній deploy у Render

Render → сервіс → **Events** → знайти попередній успішний deploy → кнопка
**Rollback**.

Швидше за revert: Render просто піднімає вже зібраний образ і не чекає на
нову збірку.

**Але код у GitHub при цьому не змінюється.** У `main` лишається зламана
версія, і наступний push у `main` задеплоїть її знову — auto-deploy не
знає, що ви відкатились.

Тому rollback у Render — це **стабілізація, а не виправлення**:

1. Rollback у Render — production знову працює (хвилини).
2. `git revert` + PR + merge — зламана зміна прибрана з `main` (розділ 8).

Без другого кроку ви отримаєте ту саму поломку при найближчій зміні —
і, найімовірніше, вже не пов'яжете її з попередньою.

## 10. Чому rollback коду не відновлює Neon

Neon — зовнішня база, вона живе окремо від коду на Render і від його
deploy'ів нічого не знає ([deploy.md](deploy.md), розділ 1).

Відкат коду повертає **застосунок**, але не **дані**. Він не скасовує:

- виконані міграції та зміни структури таблиць;
- видалені рядки;
- змінені значення.

Код відкотився — база лишилась у новому стані. Причому гірший випадок не
«дані втрачені», а «старий код працює з новою схемою»: застосунок
запускається, але падає на запитах до колонок, яких у ньому вже/ще немає.

Тому зміни структури або даних потребують **окремого плану відновлення** до
того, як їх застосовувати: бекап або зворотна міграція.

Окремо про цей проєкт: схема створюється через
`Base.metadata.create_all()` (`init_models()` у `app/db.py`), а не через
міграційний інструмент. `create_all` вміє лише **додавати** таблиці, яких
немає — він не змінює й не видаляє наявні. Тобто автоматичного механізму
зміни схеми тут немає взагалі: будь-яка правка структури робиться руками в
Neon і руками ж відкочується. Перед такою правкою — бекап.
