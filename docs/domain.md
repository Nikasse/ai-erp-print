# Власний домен для ai-erp-print

Продовження [deploy.md](deploy.md): той самий сервіс на Render, нова адреса
для користувача.

Домен: **home-base.pp.ua** (зона `.pp.ua`, реєстратор NIC.UA)
Технічна адреса Render: `ai-erp-print.onrender.com`
IP Render для A-записів: `216.24.57.1`

## 1. Що змінює домен

Нічого в архітектурі. Застосунок і далі працює на Render тим самим
Docker-образом, з тими самими змінними оточення й тією самою Neon.
Домен — це не переїзд на інший сервер, а ще один спосіб потрапити на
той самий сервер.

Ланцюг запиту:
```
home-base.pp.ua → DNS → 216.24.57.1 → Render → FastAPI → Neon
```

Адреса `ai-erp-print.onrender.com` після підключення домену продовжує
працювати — вона лишається технічною.

## 2. Реєстрація .pp.ua

Домен у зоні `.pp.ua` безкоштовний, але «безкоштовний» не означає
«в один клік». Потрібні:

- підтверджений email в акаунті NIC.UA;
- прив'язана платіжна картка — **лише для ідентифікації акаунта**,
  списань за сам домен немає;
- правильно вказаний телефон власника домену;
- окрема активація домену після реєстрації.

**Активація.** Отримати код підтвердження через Telegram-бота
[@ppuabot](https://t.me/ppuabot) або SMS, потім заповнити форму на
`apu.drs.ua`:

| Поле | Значення |
|---|---|
| Повне ім'я домену | `home-base.pp.ua` |
| Телефон власника | той, що вказаний у даних власника домену |
| Код | з Telegram-бота або SMS |

Важливо: Telegram має бути зареєстрований **на той самий номер**, який
вказано власником домену. Інакше бот код не видасть.

## 3. NS-сервери

Одразу після реєстрації домен може стояти на **паркових NS**. Симптом:
при відкритті домену показується сторінка реєстратора, а DNS-записи
редагувати нема де — зони просто немає.

Лікування: переключити домен на сервери імен NIC.UA:

```
ns10.uadns.com
ns11.uadns.com
ns12.uadns.com
```

Тільки після цього з'являється DNS-зона, в якій можна створювати записи.

## 4. Порядок дій

Порядок саме такий, і він має значення:

1. **Додати Custom Domain у Render**: Settings → Custom Domains →
   Add Custom Domain → вписати `home-base.pp.ua` — без `https://`,
   без слеша в кінці.
2. **Render показує потрібні DNS-дані.** Копіювати значення звідти, а не
   з пам'яті чи з цієї документації.
3. **Створити A-запис у NIC.UA** (розділ 5).
4. **Повернутись у Render і натиснути Verify.**
5. **Дочекатись TLS-сертифіката** — Render видає його автоматично, але
   лише після успішної верифікації.

Чому спершу Render, а не DNS: Render дає точне значення для запису під
конкретний сервіс. Поки домен не додано в сервіс, Render не знає про
нього нічого, а `Verify` не має що перевіряти.

## 5. DNS-запис

У панелі NIC.UA (DNS-записи домену) потрібен один запис:

| Name | Type | Value | TTL |
|---|---|---|---|
| `@` | `A` | `216.24.57.1` | `3600` |

- **Name `@`** — кореневий домен, тобто `home-base.pp.ua` без піддомену.
- **Type `A`** — запис, що вказує ім'я безпосередньо на IPv4-адресу.
- **Value** — IP Render.
- **TTL `3600`** — скільки секунд резолвери мають право кешувати цю
  відповідь (тут — година).

**Чому A, а не CNAME.** Render у своїх інструкціях пропонує CNAME на
`ai-erp-print.onrender.com`. Для кореневого домену це не працює: за
стандартом DNS кореневе ім'я зони не може мати CNAME (у зони вже є SOA і
NS на тому ж імені). Тому для кореня береться A-запис — Render сам про це
пише і поруч наводить IP.

**Замінити, а не додати.** У зоні NIC.UA вже є типові записи «з коробки»,
зокрема `@ → A` на IP реєстратора. Його треба **замінити** значенням
`216.24.57.1`, а не створювати другий `@ → A`. Два A-записи на одному
імені = round-robin: частина запитів іде на Render, частина — на паркову
сторінку реєстратора, і поведінка виглядає випадковою.

Записи `mail`, `ftp`, `MX` **не чіпати** — вони стосуються пошти й FTP,
до сайту відношення не мають.

## 6. Перевірка

```bash
dig home-base.pp.ua A +short
```
Що бачить резолвер твого провайдера. Може відставати — це кеш.

```bash
dig @ns10.uadns.com home-base.pp.ua A +short
```
Запит напряму на авторитетний NS — першоджерело, істина. Якщо тут
правильний IP, запис створено коректно, далі питання лише кешу.

```bash
dig @8.8.8.8 home-base.pp.ua A +short
```
Публічний резолвер Google — чи розійшлась зміна по світу.

```bash
curl -I https://home-base.pp.ua --resolve home-base.pp.ua:443:216.24.57.1
```
`--resolve` жорстко підставляє IP замість DNS-відповіді, тобто обходить
будь-який кеш і перевіряє саме Render — включно з TLS-сертифікатом на
потрібне ім'я.

```bash
curl https://home-base.pp.ua/health --resolve home-base.pp.ua:443:216.24.57.1
```
Очікуваний результат:
```json
{"status":"ok","env":"production"}
```

## 7. Типові симптоми і що вони означають

- **Відкривається паркова сторінка NIC.UA** (`Location: parkpage.nic.ua`)
  → запит іде на старий IP. Причина одна з двох: домен усе ще на паркових
  NS (розділ 3) або відповідь кешує резолвер.

- **`SSL: no alternative certificate subject name matches target host name`**
  → потрапив не на той сервер: сертифікат, який він віддає, виписаний на
  чуже ім'я. Перевіряти не TLS, а DNS — куди реально веде домен
  (`dig @ns10.uadns.com ...`).

- **`sslv3 alert handshake failure`** при зверненні напряму на IP Render
  → до Render дійшов, але сертифіката саме для цього домену ще немає:
  або не натиснуто `Verify`, або перевірка/видача триває.

- **`HTTP/2 405` із заголовком `allow: GET`** у відповіді на `curl -I`
  → це НЕ помилка. `curl -I` шле `HEAD`, а catch-all роут у
  `app/render_app.py` зареєстрований лише на `GET` (те саме, що описано
  в [deploy.md](deploy.md), розділ 6). Домен і TLS при цьому робочі —
  перевіряти звичайним `GET`, наприклад на `/health`.

- **`dig` віддає старий IP, а `dig @8.8.8.8` — новий**
  → кешує резолвер провайдера. Локальний flush кешу
  ```bash
  sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
  ```
  тут **не допоможе** — це кеш не на комп'ютері, а на стороні провайдера.
  Варіанти: дочекатись закінчення TTL, перевірити з мобільного інтернету
  (інший резолвер) або тимчасово прописати `8.8.8.8` у налаштуваннях
  мережі.

## 8. Важливе на майбутнє

Автопродовження серверів імен у NIC.UA **вимкнено**:

| Що | До якої дати |
|---|---|
| Сервери імен (NS) | 12 листопада 2026 |
| Реєстрація домену | серпень 2027 |

Дати різні, і це пастка: домен ще зареєстрований, але без активних NS він
просто перестане резолвитись — зовні це виглядатиме як «сайт зник», хоча
Render і Neon працюють. NS потрібно подовжити до 12 листопада 2026.
